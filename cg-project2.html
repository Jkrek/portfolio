Skyport Archipelago

Cube World: a volcanic island chain, a rocket launch and a ringed planet, all made of one cube

For Project 2 the only model we were allowed was a cube, so I built a whole world out of it. A chain of volcanic islands comes from two PNG images (a grayscale height map and a color map), three futuristic jets fly a looping Bézier route around them, a rocket launches off a pad on one of the islands, and a ringed gas giant hangs in the sky while the sun goes through a full day/night cycle. It's plain JavaScript and WebGL 2, no three.js or any other library. Every mountain, wing, smoke puff and star-lit planet is the same 2×2×2 cube, drawn hundreds of thousands of times.

▶ Open the live app Source on GitHub Demo video

Built for laptops with a decent GPU. The default 128×128 grid runs anywhere; 512×512 draws 262,144 cubes and needs more horsepower.

01 · Design

The plan

What I wanted the world to look like and how it should behave, before writing the code.

How it should look

A tropical volcanic archipelago at the scale of a toy: deep blue water that turns turquoise near the beaches, sand, grass, dark forest patches, gray rock and a snowcap on the big volcano with glowing lava in the crater. One island has a rocket launch site, one is an atoll with a lagoon, and a few rocky islets are scattered around. Above it, sleek white jets and a huge ringed planet make it feel a little sci-fi. I wanted the cubes to stay visible, so it reads as a cube world and not a smooth mesh.

How it should behave

The camera slowly circles the islands on its own, and you can drag to orbit and scroll to zoom. Three jets fly a loop in formation, banking into the turns. Every so often the rocket lifts off its pad, pitches over, leaves a smoke trail, disappears into the distance and is back on the pad a few seconds later. In the last level time passes: sunrise, noon, an orange sunset, then night with stars, moonlight and glowing lava, rocket flames and wingtip lights. Each project level gets its own tab so you can see the pieces build up.

A few decisions I made early

  • The terrain is always 100 × 100 world units. Changing the grid from 64² to 512² changes how many cubes there are and how big each one is, not the size of the island. So the jets' flight path and the launch pad stay in the same place at any resolution.
  • One draw call per object, not per cube. 512 × 512 is 262,144 cubes. Drawing them one at a time the way the class example does would be 262,144 draw calls every frame, so everything uses instanced drawing from the start.
  • I made my own images. Instead of downloading a height map, I wrote a small Python script that generates a matching 1024×1024 height map and color map (fractal noise, island shapes, a crater and a flat launch pad). That way the color map lines up exactly with the heights, and I could paint in features like the lava and the pad markings.

03 · Implementation

How it actually works

Where the class concepts show up in the code, roughly in the order the pipeline runs. The code is split into math.js, bezier.js, renderer.js, terrain.js, sky.js and main.js, and every file is commented section by section.

The one cube: vertices, edges and triangles

A cube has 8 corners, 12 edges and 6 faces, and WebGL can only draw triangles, so each face is 2 triangles: 12 in total. But it's stored as 24 vertices, not 8. Each corner touches 3 faces that point different ways, and a vertex can only carry one normal, so every corner is stored once per face (6 × 4 = 24). An index buffer then lists the 36 corners of the 12 triangles by number, so the 2 triangles of a face share 2 of its 4 vertices instead of repeating them. Every face is wound counter-clockwise when seen from outside, which lets back-face culling skip the faces pointing away from the camera.

// For each face: its normal n and two axes u, v that span it.
// Corners = n ± u ± v, counter-clockwise from outside (u × v = n).
for (const [su, sv] of [[-1, -1], [1, -1], [1, 1], [-1, 1]]) {
  vertices.push(n[0] + su*u[0] + sv*v[0], ..., n[0], n[1], n[2]);   // position, then normal
}
indices.push(b, b + 1, b + 2,  b, b + 2, b + 3);                    // 2 triangles per face

Translation and scaling (Levels 1a, 1b)

Each cube in the grid is the same 2×2×2 cube scaled to its cell's width and its height, then translated to its cell's center. Because the cube runs from −1 to 1, the scale is half the size, and the center sits at y = h/2 so the bottom is on the ground. In matrix form that's T · S · corner; since S is diagonal, the vertex shader just writes it out:

world = uObject · ( offset + corner ⊙ scale )    offset = (x, h/2, z)   scale = (cell/2, h/2, cell/2)

uObject is identity for the terrain. For the sky objects it carries their rotation and position (below), so the same shader handles both: each box is scaled and translated into its place on the model, then the whole model is rotated and moved into the world.

Instanced drawing: one draw call for 262,144 cubes

The class example sets a uModel uniform and issues a draw call for every cube. That's fine for 100 cubes, but at 512² the CPU spends the whole frame talking to the GPU. Instead, each batch of cubes gets a second buffer with one row per cube: offset, scale, color and a "kind" (solid, water, glowing, smoke). vertexAttribDivisor(loc, 1) tells WebGL to advance those attributes once per instance instead of once per vertex, and one call draws the whole batch:

gl.vertexAttribDivisor(LOC.offset, 1);   // advance once per CUBE, not per vertex
...
gl.drawElementsInstanced(gl.TRIANGLES, 36, gl.UNSIGNED_SHORT, 0, cubeCount);

Each batch (terrain, ocean, jet, rocket, flame, smoke, launch tower, planet, moon, debug paths) also has its own vertex array object that remembers all its bindBuffer / vertexAttribPointer / divisor settings, so switching batches is one bindVertexArray call. That avoids the bug a classmate described in Discord, where one draw call accidentally reads another program's buffers. The whole Level 4 scene is about 11 draw calls no matter the resolution.

The pinhole camera, as matrices (Level 1d)

Project 1's pinhole camera divided x and y by depth by hand. Here it's the perspective matrix: its −1 in the last column copies −z (the distance in front of the camera) into w, and the GPU divides x, y and z by w after the vertex shader. That's the same "divide by depth", which is why far cubes shrink. The field of view is 50° vertical, with near and far planes at 0.5 and 4000.

The camera position comes from an orbit, and lookAt builds the view matrix from it: three perpendicular axes from cross products (the direction to the target, right, and up), then the inverse of placing the camera, so the whole world moves until the camera sits at the origin looking down −z.

eye = target + r · (cos φ cos θ, sin φ, cos φ sin θ)    θ += speed · Δt    gl_Position = P · V · world

The depth test keeps the nearest fragment at each pixel (the hardware version of my Project 1 z-buffer), and back-face culling skips about half the triangles before they're rasterized.

Vertex colors and interpolation (Level 1c)

In Level 1c the vertex shader gives every vertex its own color from a procedure, for example a hue from its world position, or dark at the bottom and the cube's color at the top. The rasterizer then interpolates those colors across each triangle using barycentric coordinates (λ₀, λ₁, λ₂), the same weights I computed by hand in Project 1. Each fragment gets λ₀c₀ + λ₁c₁ + λ₂c₂. Lighting is off by default in that tab so you see only the interpolation. The "one color per cube" option gives all vertices the same color, so nothing changes across a face, which makes the contrast obvious.

Sampling the images (Level 2)

To read pixels, the PNG is drawn onto a hidden 2D canvas and read back with getImageData. That's blocked on file:// pages (the "tainted canvas" error a lot of us hit), because the browser treats a local image as a different origin. Served from GitHub Pages, or python3 -m http.server locally, it works. Uploaded files are read as data: URLs, which never taint the canvas, so the upload pickers work anywhere.

"The grid is 100×100 but the image is 1000×1000. How do you pick a color?" Each cube covers a block of pixels (10×10 there). The block's edges are floor(col · W / n), so it works even when W/n isn't a whole number. Then there are two options, and the app lets you switch between them:

  • Nearest: take the one pixel at the block's center. It ignores 99 of the 100 pixels, so thin features like the shoreline foam and the launch pad stripes pop in and out as the resolution changes. That's aliasing.
  • Box filter (the default): average every pixel in the block. Each cube gets the average color of the land it stands for. It's a simple low-pass filter, the same idea as mipmapping a texture before shrinking it.

"Gray goes from 0 to 255. How do you turn that into a height?" Normalize, apply a curve, then scale:

f = (gray / 255)k    height = f · maxHeight    (k = 1.3, maxHeight = 24 by default)

A curve k > 1 flattens the lowlands and sharpens the peaks, which looks more like a volcano; k < 1 does the opposite. Anything darker than the sea level gray (64) is underwater: its cube is cut off at the water surface and marked as water, so the shader can animate waves and add a sun glint. The color map still decides its color, which is how deep water is dark and shallow water is turquoise. A single huge flat cube just under the surface extends the ocean to the horizon.

Bézier curves with de Casteljau (Level 3)

Every moving thing follows cubic Bézier curves: four control points P0…P3. To find the point at parameter t, I use de Casteljau's construction, the same method as the class's guided subdivision activity. Cut each segment of the control polygon at the fraction t, then cut the new segments, until one point is left:

function deCasteljauLevels(points, t) {
  const levels = [points];
  let current = points;
  while (current.length > 1) {
    const next = [];
    for (let i = 0; i < current.length - 1; i++) next.push(vec3.lerp(current[i], current[i + 1], t));
    levels.push(next);                    // P01 P12 P23 → P012 P123 → P0123 = B(t)
    current = next;
  }
  return levels;
}

That gives exactly the same point as the Bernstein form B(t) = (1−t)³P0 + 3(1−t)²t P1 + 3(1−t)t² P2 + t³P3, but it's built only from "the point a fraction t along a segment". It also gives two things for free:

  • The tangent. The two points on the second-to-last level, P012 and P123, lie on the curve's tangent line at B(t). Their difference (normalized) is the direction of travel, which is what points the jets and the rocket.
  • Subdivision. The left and right edges of the de Casteljau triangle are the control points of the two halves of the curve. The "show paths" option cuts each segment at t = ½ recursively until it passes a flatness test (the inner control points are within a tolerance of the chord P0→P3), and draws a small cube at each piece's end. The dots bunch up where the curve bends and spread out where it's straight. The tolerance slider shows the point count change live.

The jets: a smooth loop, constant speed, banking

The jets' route is six anchor points around the islands, joined into a closed loop of six cubic segments. For the joins to be smooth (C1 continuous, no kink), the handle before an anchor, the anchor and the handle after it have to be on one straight line at equal distances. I pick each anchor's direction from its two neighbors, the way a Catmull-Rom spline does, and put the handles a third of that away:

Ti = (Ai+1 − Ai−1) / 2    P0 = Ai   P1 = Ai + Ti/3   P2 = Ai+1 − Ti+1/3   P3 = Ai+1

Constant speed. Moving t at a steady rate doesn't move the jet at a steady speed. Points crowd together where control points are close and spread out where they're far apart (the guided activity's "does t = ½ cut the curve into equal lengths?" question, and the answer is no). So I sample the path once, add up the distances into a table of (t, distance), and each frame look up t by distance with a binary search. That's arc-length parameterization. Uncheck "constant speed" and you can watch the jets speed up and slow down.

Pointing and banking. To orient a jet I build a rotation whose columns are its new axes: forward is the tangent, right and up come from cross products with world up (Gram-Schmidt, like lookAt). To bank, I compare this tangent with one a little further along the path; the vertical part of their cross product says how hard and which way it's turning, and I tilt the up vector by that much before taking the cross products. The two wingmen are the same path sampled 9 units behind, shifted ±7 sideways.

const right = normalize(cross(upRef, forward));
const up    = cross(forward, right);
uObject = fromBasis(right, up, forward, position) · scaling(0.8);   // rotate + translate the whole jet

The rocket: one cubic, ease-in, and "far away"

The rocket's flight is a single cubic. P0 is on the pad and P1 is straight above it, so the tangent at t = 0 points straight up and the rocket starts upright with no special case. P2 is high and off to the side and P3 is hundreds of units away, so it pitches over and leaves. Instead of moving t steadily I use t = τ² (τ = fraction of the 11-second flight), so it starts slow and accelerates like a real launch. When t reaches 1 it's far away, so it's hidden for 3 seconds and then put back on the pad, exactly what the spec described. The flame is a few glowing cubes with random sizes every frame (flicker), and the smoke trail is cubes dropped at the tail that grow, rise and then shrink to nothing.

The planet: rotation and composition

The gas giant is made by testing every cell of a 31³ grid and keeping only a thin spherical shell (you can never see the inside, so that saves thousands of cubes). It's colored by latitude bands with a red storm, plus a flat ring with a gap. Its transform is a chain: scale the grid, spin it about y, tilt it, then move it out into the sky. The moon adds an orbit: rotate around the planet, then push out.

planet = T(center) · Rz(0.42) · Ry(0.04 t) · S(3)    moon = T(center) · Rz(0.42) · Ry(0.12 t) · T(112, 10, 0) · Ry(0.3 t) · S(2.6)

Because the transforms only rotate, translate and scale uniformly, mat3(uObject) turns the normals correctly. In general (non-uniform scaling inside the object matrix) you'd need the inverse transpose; here each box's own non-uniform scaling is along the cube's axes, which doesn't change the direction of a face normal.

Lighting, the skybox and fog (Level 4)

  • Diffuse: Lambert's cosine law, brightness = max(n · l, 0) with both unit vectors, toward the sun by day and the moon by night. Both fade to zero at the horizon, so the hand-off is smooth.
  • Ambient: a hemisphere light. Faces pointing up get the sky's color, faces pointing down the ground's, blended by n.y.
  • Water glint: a Blinn-Phong specular highlight using the half vector between the light and the view direction.
  • Smoke: "half-Lambert" wrap lighting, n · l × ½ + ½, so smoke turned away from the sun stays soft instead of black.
  • Glow: lava, flames, the canopy and lights skip lighting entirely and get brighter at night.

The sun moves on a tilted circle (rising in +x at 06:00, setting in −x at 18:00), and almost everything is a smooth function of its height above the horizon: the zenith and horizon colors, the orange sunset tint, the light color, the ambient light, how many stars show and how bright the glowing cubes are.

The skybox is the same cube, drawn around the camera. I remove the camera's translation from the view matrix (so the sky never gets closer), cull the front faces (we're inside it), and set gl_Position = clip.xyww so every sky fragment lands at depth 1.0, behind everything. The fragment shader gets the interpolated direction to each fragment and computes the sky for that direction: a gradient by elevation, a sun disc and glow, the moon, and stars from hashing the direction into small cells.

Fog fades each fragment toward the horizon color by distance, 1 − exp(−(d · density)²), which hides the edge of the ocean and makes the planet feel far away (it gets a thinner fog than the island).

I still kept 128² as the default because the spec asks for something that works on most laptops, and integrated graphics on an older machine is a lot weaker than this one. The real limit at high resolutions is the vertex work (24 vertices × 262k cubes ≈ 6.3 million vertices per frame), not draw calls.

04 · Future work

What I'd do next

  • Shadows. Render the scene from the sun into a depth texture and compare against it (shadow mapping). The sunset would look a lot better with the volcano casting a long shadow across the island.
  • Skip hidden faces. Most cube walls are buried against their neighbors. Only drawing the faces that are exposed, or merging flat runs of cubes into bigger boxes (greedy meshing), would cut the vertex count several times over.
  • Sample the images on the GPU. Load the maps as textures and look up height and color in the vertex shader, so changing the resolution is instant instead of rebuilding on the CPU.
  • A free-fly camera. WASD plus mouse look, in addition to the orbit and chase cameras.
  • More life in the sky. Drifting cube clouds with transparency, and a few more aircraft on different curves.
